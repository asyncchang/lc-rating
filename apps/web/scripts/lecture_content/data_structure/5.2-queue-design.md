## 這個技術解決什麼問題

設計題問的不是「怎麼算出答案」，而是「**在給定的操作集合與複雜度要求下，該用什麼狀態去表示這個抽象型別**」。本節的題目分成三類：

- **用 A 模擬 B**：232（用堆疊實現佇列）、225（用佇列實現堆疊）。核心是**順序的轉換代價**。
- **固定容量的環形結構**：622（設計循環佇列）、641（設計循環雙端佇列）。核心是**取模算術與空／滿的區分**。
- **多容器分工**：1670（設計前中後佇列）、3508（設計路由器）。核心是**用一組不變量把「中間」或「過期」變成某個容器的端點**。

**共通的解題流程**：先寫下每個操作的目標複雜度 → 反推「什麼必須是 $O(1)$ 可取得的」 → 設計狀態使那些量都落在某個容器的端點或某個維護好的變數上 → 最後才寫程式。**先想不變量，再寫程式碼，順序反過來一定會漏 case。**

## 狀態／資料結構定義

### 232 用兩個堆疊實現佇列

```
stack<int> in;   // 新元素進這裡
stack<int> out;  // 舊元素從這裡出
```
**狀態解讀**：邏輯佇列（由前到後）＝ `out` 由頂到底，接上 `in` 由底到頂。

### 225 用佇列實現堆疊

只需一個 `queue<int> q`。`push(x)` 時先 `q.push(x)`，再把前面的 `q.size()-1` 個元素依序彈出並重新入隊（「自旋」）。**狀態解讀**：`q` 的頭端永遠是「最後推入的元素」。

### 622 設計循環佇列

```
vector<int> buf;   // 大小 = capacity
int head = 0;      // 隊首下標
int cnt = 0;       // 目前元素個數
```
**用 `cnt` 而不是 `tail`。** 只存 `head`／`tail` 時，`head == tail` 同時代表「空」與「滿」，必須犧牲一個格子來區分（容量 $k$ 就開 $k+1$）。**維護 `cnt` 可以用滿全部空間，而且 `isEmpty`／`isFull` 直接讀，少一類 bug。** 寫入位置是 `(head + cnt) % capacity`。

### 641 設計循環雙端佇列

同上，多一個前端插入：`head = (head - 1 + capacity) % capacity`。**必須加 `capacity` 再取模**——C++ 的 `%` 對負數回傳負數（`-1 % 5 == -1`），這是本節最常見的 runtime error 來源。

### 1670 設計前中後佇列

```
deque<int> A, B;   // A 是前半，B 是後半；邏輯序列 = A 接 B
```
**不變量 (I)**：$|A| = \lfloor n/2 \rfloor$，$|B| = \lceil n/2 \rceil$，其中 $n = |A| + |B|$。
**這條不變量的用途**：把「中間」變成 `A.back()` 或 `B.front()`，於是四個位置（前、中、後）全都是某個 `deque` 的端點，全部 $O(1)$。

### 3508 設計路由器

```
queue<array<int,3>> fifo;                    // 記憶體上限的淘汰順序
set<array<int,3>> seen;                      // 去重（同 (src,dst,ts) 只留一份）
unordered_map<int, vector<int>> ts;          // 每個目的地的時間戳（遞增）
unordered_map<int, int> startIdx;            // 該目的地已被淘汰掉的前綴長度
```
**`ts[d]` 用 `vector` 加一個起始下標，不用 `deque` 也不真的刪除**——因為要對它做二分搜尋。**惰性刪除 + 有序陣列 = 可二分的滑動視窗**，這個組合在離線題（12.x）中會再出現。

## 不變量或正確性證明

### 定理 1（232 的搬移時機：為什麼「只在 `out` 空時才倒」）

*不變量 (Q)*：任一操作結束後，邏輯佇列由前到後 $=$ `out` 由頂到底，接上 `in` 由底到頂。

*證明*。`push(x)` 把 $x$ 放到 `in` 頂端，也就是邏輯序列的最後 —— (Q) 保持。
`pop()`／`peek()` 時若 `out` 非空，取 `out.top()` 即邏輯最前者 —— (Q) 保持。
若 `out` 為空，把 `in` 整個搬到 `out`：搬移是逐個 `out.push(in.top()); in.pop();`，等於把 `in` 反轉。原本邏輯序列 $=$ `in` 由底到頂 $= (x_1, \dots, x_m)$；搬完後 `out` 由頂到底也是 $(x_1,\dots,x_m)$ —— (Q) 保持。$\square$

**為什麼必須「`out` 空才搬」？** 若 `out` 還有 $(y_1,\dots,y_k)$ 而把 `in` 的 $(x_1,\dots,x_m)$ 倒上去，`out` 由頂到底變成 $(x_1,\dots,x_m,y_1,\dots,y_k)$，但正確順序是 $(y_1,\dots,y_k,x_1,\dots,x_m)$——**順序被破壞**。這不是效率問題，是正確性問題。

*攤還分析*：令位能 $\Phi = |{\tt in}|$。`push` 實際成本 1、$\Delta\Phi = +1$，攤還 2。一次觸發搬移的 `pop` 實際成本 $m+1$、$\Delta\Phi = -m$，攤還 1。**每個元素一生最多被搬移一次**，故 $q$ 次操作總計 $O(q)$，**攤還 $O(1)$**。

### 定理 2（225 為什麼做不到攤還 $O(1)$：模擬是有方向的）

232 能攤還 $O(1)$，225 不能——**這個不對稱不是巧合。**

*論證（黑盒模型：只能用佇列介面 `push`／`pop`／`front`／`size`）*。設佇列中目前有 $k+1$ 個元素，我們要取出「最後推入」的那一個。由 FIFO 語意，唯一能讀到的是頭端；要讓目標元素浮到頭端，必須先把排在它前面的 $k$ 個元素取出。每次取出只能移動一個元素，故成本 $\Omega(k)$。$\square$

**根本差別**：**堆疊的 `pop` 天生產生逆序，佇列的任何操作都保序。** 「把佇列變成堆疊」需要製造逆序，而逆序無法用保序操作攤還地製造；「把堆疊變成佇列」只需要一次逆序，而堆疊本來就免費提供。

*實作上的取捨*：`push` $O(n)$／`pop` $O(1)$，或 `push` $O(1)$／`pop` $O(n)$，兩種都對，**選哪種取決於題目的操作分佈**；LeetCode 沒有給分佈，習慣寫前者（自旋在 `push`）。

### 定理 3（622 環形佇列的位址不變量）

*不變量 (C)*：邏輯上第 $i$ 個元素（$0 \le i < cnt$）存在 `buf[(head + i) % capacity]`。

*證明*。初始 $cnt = 0$，真空成立。
- `enQueue(v)`（要求 $cnt < capacity$）：寫入 `buf[(head + cnt) % capacity]`，然後 $cnt{+}{+}$。新元素的邏輯下標正是舊的 $cnt$，位址吻合 —— (C) 保持。
- `deQueue()`（要求 $cnt > 0$）：`head = (head+1) % capacity; cnt--;`。原本邏輯下標 $i$ 的元素變成 $i-1$，而位址 $(head_{new} + (i-1)) \% cap = (head_{old} + i) \% cap$ 不變 —— (C) 保持。$\square$

*推論*：`Front()` $=$ `buf[head]`，`Rear()` $=$ `buf[(head + cnt - 1) % capacity]`。**`Rear()` 不能寫成 `buf[tail - 1]`——`tail` 可能是 0。**

**空／滿的區分**：本設計用 $cnt$ 判斷，$cnt = 0$ 空、$cnt = capacity$ 滿，**兩者不會混淆**。若改用 `head`／`tail` 雙指標，$head = tail$ 同時代表空與滿，資訊量不足以區分 —— 因為 $(head, tail)$ 只有 $capacity^2$ 種狀態，卻要表示 $capacity + 1$ 種大小加上位置，鴿籠原理保證必有碰撞。**犧牲一格（只允許存 $capacity - 1$ 個）或多存一個 `cnt`／`bool full`，是僅有的三種修法。**

### 定理 4（1670 的平衡不變量與 `pushMiddle`／`popMiddle` 的位置）

題目定義：`pushMiddle` 插入到下標 $\lfloor n/2 \rfloor$（$n$ 為插入前的長度）；`popMiddle` 刪除下標 $\lfloor (n-1)/2 \rfloor$（有兩個中間時取靠前者）。

在不變量 (I)（$|A| = \lfloor n/2\rfloor$）下：

- **`pushMiddle`**：目標下標 $\lfloor n/2 \rfloor = |A|$，也就是 $B$ 的第 0 個位置 ⇒ `B.push_front(v)`。
- **`popMiddle`**：目標下標 $\lfloor (n-1)/2 \rfloor$。
  - $n$ 偶數：$\lfloor (n-1)/2\rfloor = n/2 - 1 = |A| - 1$ ⇒ `A.back()`。
  - $n$ 奇數：$\lfloor (n-1)/2 \rfloor = (n-1)/2 = |A|$ ⇒ `B.front()`。

  **這個 case split 是題目「兩個中間取靠前者」直接推出來的，不是實作偏好。** 寫錯就是把偶數長度的中間取到後面那個。

*再平衡*：每個操作後恢復 (I)。若 $|A| > \lfloor n/2\rfloor$，把 `A.back()` 搬到 `B.push_front`；若 $|A| < \lfloor n/2 \rfloor$，把 `B.front()` 搬到 `A.push_back`。**每次操作最多搬一個元素**（因為每個操作只讓 $n$ 變動 1、只讓某一側變動 1，偏差量至多為 1），故仍是 $O(1)$。

*邊界*：$n = 0$ 時 `popFront`／`popMiddle`／`popBack` 回傳 $-1$；$n = 1$ 時 (I) 給 $|A| = 0, |B| = 1$，`popMiddle` 走奇數分支取 `B.front()` ✔。**用 $n = 0,1,2,3$ 各手算一次，是驗證這類設計題最有效的方法。**

### 定理 5（3508 惰性淘汰 + 二分：兩個前提）

`addPacket` 超過記憶體上限時淘汰最舊的封包；`getCount(dst, lo, hi)` 問某目的地在時間區間內的封包數。

*不變量*：對每個目的地 $d$，`ts[d]` 是一個**遞增**序列，其中下標 $\ge$ `startIdx[d]` 的部分恰好是「仍在記憶體中、目的地為 $d$」的封包時間戳。

*前提 1（時間戳單調）*：題目保證 `addPacket` 的 `timestamp` 非遞減，所以 `ts[d]` 天然遞增，**才能二分**。若亂序，得改用 `multiset` 或離線排序。
*前提 2（淘汰順序 = 加入順序）*：FIFO 淘汰保證被移除的一定是 `ts[d]` 的**前綴**，所以只要推進 `startIdx[d]`，不必真的從 `vector` 中刪除。$\square$

*查詢*：在 `ts[d]` 的 `[startIdx[d], end)` 區間上做兩次二分（`lower_bound(lo)`、`upper_bound(hi)`），相減即答案。

**這兩個前提和 5.1 定理 1 是同一條**：**「過期／被淘汰者恆為前綴」是所有惰性刪除的共同基礎。**

## 時間與空間複雜度

| 題目 | 操作 | 時間 | 空間 |
| --- | --- | --- | --- |
| 232 用堆疊實現佇列 | `push`／`pop`／`peek`／`empty` | 攤還 $O(1)$（單次最壞 $O(n)$） | $O(n)$ |
| 225 用佇列實現堆疊 | `push` | $O(n)$ | $O(n)$ |
| 225 | `pop`／`top`／`empty` | $O(1)$ | |
| 622 循環佇列 | 全部 | $O(1)$ 最壞 | $O(k)$ |
| 641 循環雙端佇列 | 全部 | $O(1)$ 最壞 | $O(k)$ |
| 1670 前中後佇列 | 全部 | $O(1)$ 最壞 | $O(n)$ |
| 3508 路由器 | `addPacket` | 攤還 $O(\log n)$（`set` 去重） | $O(m)$，$m$ 為記憶體上限 |
| 3508 | `forwardPacket` | 攤還 $O(\log n)$ | |
| 3508 | `getCount` | $O(\log n)$ | |

**「攤還 $O(1)$」與「最壞 $O(1)$」在面試中是不同的答案。** 232 是攤還，622／641／1670 是最壞——**環形陣列與多容器分工之所以值得寫，正是因為它們給出最壞情況保證**。若題目提到即時系統或延遲上限，攤還就不夠了。

**3508 的空間**：`ts[d]` 用 `vector` + `startIdx` 惰性刪除，**被淘汰的前綴不會回收**，最壞空間是「歷史上出現過的全部封包數」而非記憶體上限。若操作數極大，需定期做一次 `erase(begin, begin+startIdx)` 壓縮（攤還仍 $O(1)$，因為只在 `startIdx > size/2` 時做）。**這是惰性刪除的固定代價，答題時要主動提。**

## 與相似技巧的比較

- **與 4.2 堆疊設計題**：兩者的方法論相同——**先列出每個操作要 $O(1)$ 拿到什麼，再設計狀態讓那些量落在端點上**。差別在 4.2 可以「回滾」（LIFO 保留歷史），本節多半不行，所以更依賴「多容器分工」。
- **與 4.6 相向雙棧**：1670 的兩個 `deque` 和 4.6 的 gap buffer 是同一個想法——**把「中間」變成兩個容器的介面**。4.6 的介面是游標，1670 的介面是中位；4.6 的平衡由使用者的移動決定，1670 的平衡由不變量 (I) 強制維持。
- **與 6.6 對頂堆**：4.6 定理 3 的雙堆求中位數與 1670 形狀極像，但**目標不同**：對頂堆要的是「值的中位數」（所以用堆，按值分割），1670 要的是「位置的中間」（所以用 deque，按下標分割）。**看清楚「中間」指的是值還是位置，是這兩題唯一的分歧點。**
- **與 5.1 普通佇列**：622 是 `queue` 在固定容量下的手工實作。**面試問「你會怎麼實作 `std::queue`」，答案就是 622 或分塊鏈結串列。**
- **與 9.x 樹狀陣列**：3508 的 `getCount` 若時間戳亂序，就要換成「以時間為下標的樹狀陣列」，$O(\log n)$ 單點加、區間求和。**有序 + 二分是 $O(\log n)$；無序就要付出結構的代價。**
- **與 12.x 離線演算法**：3508 的「惰性刪除 + 前綴指標」正是離線掃描的縮影。**只要刪除順序固定且與查詢無關，就可以不刪，只推指標。**

## 本節重點速查

**設計題的流程**：列出操作與目標複雜度 → 反推哪些量必須 $O(1)$ 可得 → 設計狀態讓它們落在端點或維護變數上 → 寫下不變量 → 最後才寫程式。
**232**：兩堆疊，**只在 `out` 為空時才把 `in` 倒過去**（否則順序錯，是正確性 bug 不是效率問題）；位能 $\Phi=|{\tt in}|$ ⇒ 攤還 $O(1)$。
**225**：`push` 自旋 $O(n)$。**做不到攤還 $O(1)$**——堆疊的 `pop` 免費製造逆序，佇列的所有操作都保序（定理 2）。
**622／641**：維護 `head` + `cnt`，**不要用 `head`／`tail` 雙指標**（$head=tail$ 空滿不分，鴿籠原理保證資訊不足）。寫入位置 `(head+cnt)%cap`，前端插入 **`(head-1+cap)%cap`——負數取模必須先加 `cap`**。
**1670**：不變量 $|A|=\lfloor n/2\rfloor$；`pushMiddle` ⇒ `B.push_front`；`popMiddle` 偶數取 `A.back()`、奇數取 `B.front()`（由「兩個中間取靠前者」推得）；每次操作最多搬一個元素。
**3508**：惰性淘汰只推 `startIdx`，靠**「淘汰順序 = 加入順序 ⇒ 被刪者恆為前綴」**與**「時間戳單調 ⇒ 可二分」**兩個前提；空間不會自動回收，要主動說明或定期壓縮。
**攤還 $O(1)$ ≠ 最壞 $O(1)$**：232 是攤還，622／641／1670 是最壞。有延遲上限的場合只有後者可用。
用 $n = 0,1,2,3$ 手算一遍，是驗證設計題最有效的方法。
